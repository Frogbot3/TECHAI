# TECH AI demo audit — 4 October 2026

Changes are local to this repository; the deployed site and Razorpay dashboard have not been changed.

| Issue | Evidence and focused change |
| --- | --- |
| 1. MongoDB timeouts | Reproduced `MongoOperationTimeoutError` when reading full product/order payloads. Small indexed queries took roughly 50–70 ms, while large primary reads could exceed 15 seconds. Some product documents contain nearly 2 MB of inline image data. Kept the existing global Mongoose cache, made the connection promise survive concurrent requests/hot reloads, increased pool capacity to 10 and idle lifetime to 60 seconds. Selection/connect limits are 10 seconds, socket limit 20 seconds, operation limit 15 seconds. Orders retain primary reads for payment freshness but exclude inline images; a separate authenticated endpoint serves snapshot images. Default order page is 50, capped at 200, with a Load older orders control. Product catalog reads use `secondaryPreferred`, which also supports deployments without secondaries. Added structured error types, operation names and request IDs. |
| Existing order indexes | Verified the actual database already has `{customerId:1,createdAt:-1}`, `{status:1,createdAt:-1}` and `{createdAt:-1}`. This app uses `customerId`, not `userId`. No redundant indexes, joins or populates were added to order history. |
| 2. Hero price mismatch | Confirmed the stored Dell campaign price was 39,990 and was preferred over the product price. Campaign output now derives price, MRP and discount from its linked product; create/update also stores product values. Admin price fields are read-only. The carousel prefers the current catalog product over an older embedded campaign product. |
| 3. Hero copy mismatch | Confirmed the Dell campaign and another campaign contained microwave copy. Changing a product previously retained the old subtitle. Hero descriptions now come from the linked product; product selection resets the description and the admin field displays catalog copy. Legacy stored campaign copy is ignored when rendering. |
| 4. Blank/broken images | Confirmed the companion card had no error handler, and the main hero fallback could retry the same broken URL. Added deduplicated fallback attempts, a local neutral placeholder, source-change reset and loading indicators. Product cards retain their existing fallback and now indicate loading. Browser rendering could not be verified because no browser is connected. |
| 5. Wrong product imagery | Catalog data uses generic external photography, but the precise pictured model could not be visually verified. Added server URL validation and an admin browser load check for all image sources before saving. Admins must confirm that previews match the product's brand/model. This does not automatically establish that an image depicts the correct model; no replacement image was guessed. |
| 6. Paid order showing Pending | Signature verification and server-computed prices already existed. The webhook handled refunds only. Added signed `payment.captured` and `payment.failed` handling sharing atomic transitions with the callback. Captures check gateway order, amount and INR currency; late failures cannot downgrade Paid. The browser failure endpoint now fetches Razorpay's payment before changing state. Actual gateway method updates the order's method. Admin edits cannot override online payment state. |
| 7. Failure, abandonment and refunds | Checkout dismissal already leaves the order pending for retry. Verified real Razorpay TEST order creation and fetched its unpaid state. Called the real refund API with a nonexistent test payment and confirmed rejection (404). Existing refund approval genuinely calls Razorpay's refund API. Fixed ambiguous API timeouts to retain REFUND_PROCESSING and reserved funds until reconciliation, rather than freeing the refund for another attempt. Refund webhooks check payment/amount and cannot downgrade a completed refund; repeated events repair order totals after partial processing. |
| 8. Admin/security | All protected `/api/admin/*` handlers already checked the admin session. Login/session/logout intentionally remain authentication entry/inspection/clearing endpoints. Found and closed an unprotected `/api/customers` directory. Added a MongoDB-backed budget of 20 admin login attempts per 15-minute window and Retry-After, constant-time password comparison, 8-hour admin sessions, explicit JWT algorithm/role validation and removal of fallback signing secrets. JWT_SECRET must have at least 32 characters. Tightened Firebase issuer/algorithm/time checks and escaped email/search regexes. `.env.local` is ignored, not tracked and absent from reachable Git history. A scan of five configured private values found no matches in tracked source or generated browser bundles; this is not an exhaustive historical secret audit. |
| 9. Delivery header | Confirmed the literal Mumbai 400001 default. Header now uses the last saved address's city/pincode, updates after checkout, and shows Select location when unavailable. Manual location selection remains available. |
| 10. Customer duplicates | The two jiyad records have no shared email/phone, Firebase UID or recorded login; there is no evidence to merge them. No duplicate normalized email groups were found. Four other legacy records share a stored phone, which may be unverified delivery data. Checkout no longer overwrites login email/phone with delivery contacts. Added normalized-email/Firebase UID uniqueness and a separate unique verifiedPhone field populated only from verified Firebase claims. A known Firebase identity takes precedence; ambiguous legacy linking returns a conflict instead of choosing an arbitrary user. No customer records or order ownership were destructively merged. |

## Verification

- `npm test`: 16 passing regression tests. Covers pricing/copy, pagination and regex safety, image URL validation, forged signatures, payment races and event reordering, protected admin handlers, refund API contract/rejection, uncertain refund timeout, session lifetime, rate limiting, shared MongoDB connections, and snapshot image ownership.
- `npx tsc --noEmit`: passed.
- Production builds passed. `NEXT_DIST_DIR=.next-audit` isolates verification output from the user's existing development server; the first shared-output preview failed because both processes wrote `.next`.
- HTTP smoke checks on the running app: unauthenticated customer directory/admin endpoints returned 403; orders returned 401. A warm catalog request returned 59 products in about 2.1 seconds, a synthetic customer history returned in 105 ms, three campaigns returned in 662 ms, and a real 50-order admin history returned in 1.65 seconds. These are individual measurements, not load-test percentiles or an Atlas/network SLA.
- The MongoDB user denied access to a disposable integration database (code 8000); real-database concurrency assertions were not run. Production customer/order records were not used as test fixtures.
- `node tests/services-smoke.cjs` exercised the real Razorpay TEST API. It leaves unpaid ₹1 test orders in the test dashboard; it does not charge or refund a real payment. It reports skipped database tests explicitly.
- No browser is connected. Visual layout, image-error behavior, saved-address rendering and the full Google/OTP/checkout UI flows remain unverified in a browser.
